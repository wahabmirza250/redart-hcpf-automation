# RedArt Colorado Medicaid 837P Validator

This service is a preflight gate for Colorado Medicaid professional claims.
It is intentionally separate from the Playwright HCPF portal robot.

## What it does

1. Receives the generated X12 837P plus the submitting company's Colorado TPID.
2. Runs `pyx12==4.0.0` against `005010X222A1`.
3. Returns pyx12's structured validation errors and locally generated 999.
4. Applies Colorado-specific companion-guide rules that generic pyx12 cannot know.
5. Returns `ready_for_sftp=true` only when both layers pass.

## Important acknowledgment rule

The `local_999` returned by this service is generated by pyx12. It proves only
that our local validator processed the file. It is **not** an acknowledgment
from Colorado/HCPF and must never update a claim to `acknowledged`.

After an actual SFTP submission, RedArt must independently retrieve the real
HCPF TA1/999/277CA response and correlate it using ISA13, GS06, and ST02.

## Colorado rules currently enforced

The state-specific layer is based on the Colorado Medical Assistance Program
837P companion guide (June 2025, version 2.5):

- exactly one ISA per inbound file
- ISA05/ISA07 = `ZZ`
- ISA06 = the submitting company's dynamic Colorado TPID
- ISA08 = `COMEDASSISTPROG`
- ISA12 = `00501`
- ISA15 = `T` or `P`, matching the requested mode
- GS01 = `HC`
- GS02 = the same dynamic TPID
- GS03 = `COMEDASSISTPROG`
- GS08/ST03 = `005010X222A1`
- BHT06 = `CH` for fee-for-service or `RP` for encounters
- receiver name/id = Colorado Medical Assistance Program / `COMEDASSISTPROG`
- subscriber qualifier = `MI` with a non-empty Colorado Client ID
- payer qualifier/id = `PI` / `CO_TXIX`
- SBR09 = `MC` for normal Medicaid or `16`/`MA`/`MB` for crossover claims
- CLM05-3 must be `1`, `7`, or `8`
- frequency `7`/`8` requires the payer claim control number (`REF*F8`)
- `PWK` is blocked because the current Colorado 837P companion guide does not support it

pyx12 remains responsible for base HIPAA/X12 implementation-guide validation.
Passing both validators improves submission quality but does not guarantee payer
adjudication or prove transmission/receipt.

## API

### Health

`GET /health`

### Validate Colorado 837P

`POST /v1/colorado/837p/validate`

Request body:

```json
{
  "x12": "ISA*...~GS*...~...",
  "tpid": "COLORADO_TPID_FROM_COMPANY_CONFIG",
  "usage": "T"
}
```

Response decision:

```json
{
  "ready_for_sftp": true,
  "pyx12": {
    "version": "4.0.0",
    "valid": true,
    "local_999_is_state_acknowledgment": false
  },
  "colorado": {
    "valid": true,
    "errors": []
  }
}
```

## Authentication

The validation endpoint fails closed by default because 837 files contain PHI.
Set `EDI_VALIDATOR_TOKEN` in every deployed environment and have RedArt send the
same value in the `X-Service-Token` header.

For isolated local development only, token checking can be disabled with:

```bash
EDI_VALIDATOR_ALLOW_INSECURE_LOCAL=1
```

Do not set that variable on Railway or any internet-accessible environment.

## Local run

```bash
cd edi-validator
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
export EDI_VALIDATOR_ALLOW_INSECURE_LOCAL=1
uvicorn app:app --host 0.0.0.0 --port 8080
```

## Railway

Create a separate Railway service from this repository and set its root/build
context to `edi-validator`. Do not replace the existing portal-robot service.
Set `EDI_VALIDATOR_TOKEN` as a Railway secret before connecting RedArt.

## Production submission gate

The SFTP sender should use this rule:

```text
build 837P
  -> validate with pyx12
  -> validate Colorado rules
  -> if either fails: Need Attention; DO NOT SEND
  -> if both pass: upload once to HCPF SFTP
  -> persist ISA13/GS06/ST02 + filename + sha256
  -> wait for real HCPF TA1/999/277CA
  -> correlate acknowledgment to the persisted controls
```

The validator itself does not upload claims. That separation prevents a
validation retry from accidentally causing a duplicate submission.
